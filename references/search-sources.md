# 搜索来源与查询策略

仅在需要外部发现、来源降级或中文生态补充时读取本文件。

## 查询设计

从用户任务生成有限查询集：

1. 一个表达最终任务的主要英文查询；
2. 最多两个常见相邻词、行业术语或缩写；
3. 中文词在中文来源或中文 GitHub 内容可能改变结果时保留一个中文查询。

优先扩展“任务含义”，不要只机械翻译产品名。例如：

- “用户认证”可关联 `authentication`、`auth`、`oauth`；
- “Word 排版”可关联 `docx formatting`、`Microsoft Word`；
- “Unity MCP 自动化”应先区分要找的是 Agent Skill、MCP server，还是普通 Unity 工具。

总查询数通常不超过四个。每个查询应能说明为什么可能找到不同候选。

## 来源层级

### 0. 本地已安装 Skill

检查客户端已暴露的 Skill 列表，以及当前项目、用户和插件范围内的 Skill 元数据。优先匹配 `name`、`description` 和实际任务范围。

报告检查到的范围和不可访问的范围。找到直接匹配后停止，除非用户要求比较。

### 1. Skills CLI 与 skills.sh

优先使用环境中已经可用的 Skills CLI；在执行前查看当前帮助，避免依赖记忆中的参数。skills.sh 可作为目录和安装量信号，但其摘要、排名和数量都不是安全或质量证明。

权威入口：

- <https://github.com/vercel-labs/skills>
- <https://skills.sh/>

不要为了搜索而自动安装或升级 CLI。

### 2. GitHub 规范仓库

搜索包含 `SKILL.md` 的原始仓库、可信组织仓库和项目官方仓库。优先打开规范仓库和具体 Skill 路径，而不是聚合站的缓存副本。

GitHub 搜索或 API 需要认证时，先使用现有认证；不要自动登录、索取令牌或改变用户配置。认证不可用时，使用普通网页搜索或可访问的公开仓库页面，并报告降级。

### 3. 中文或其他目录

只有以下情况才进入本层：

- 前两层没有可信直接匹配；
- 用户明确要求中文生态、本地化内容或某个目录；
- 目标产品的官方 Skill 主要发布在其他目录。

现场验证目录是否可访问、是否支持搜索、是否指向规范源码、结果是否新鲜。没有规范仓库或完整载荷的条目只能作为线索，不能进入可安装推荐。

不要维护庞大静态渠道表，也不要记忆目录规模、固定 API 或“官方认证”状态。

## 每个来源的健康记录

记录：

- 来源名称和查询时间；
- 使用的查询词；
- 成功、失败、认证受限或部分结果；
- 返回的候选数量；
- 索引或结果时间信息（可获得时）。

一个来源失败不应阻断其他独立来源。最终答案要说明搜索是否完整。

## 候选元数据

初始搜索阶段只收集：

- 名称和一句话说明；
- 规范仓库网址；
- Skill 路径；
- 发布者或组织；
- 安装量、Stars、更新时间等现场可验证信号；
- 已安装状态；
- 候选类型：Skill、MCP、Plugin、Agent 或普通项目。

不要在这一阶段执行或安装候选内容。

## 去重与短名单

使用规范仓库网址和 Skill 路径作为身份。镜像、分叉、市场快照和上游原版应分开标记。

先按任务匹配排除无关结果，再从剩余候选中选择最多三个进入完整审查。Popularity 只能在任务匹配近似时作为辅助信号。

停止继续搜索的条件：

- 用户没有要求比较，且已有完整可审查的直接匹配；
- 当前候选已覆盖用户关键约束，新增来源不太可能改变结论；
- 所有可访问来源都失败或只返回无法审查的线索，此时报告受阻。

用户明确要求比较时，应尝试形成至少两个可审查候选；若只有一个，报告已查范围和没有第二候选的原因。
